This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

NEShim — NES emulator on BizHawk's cycle-accurate core, native Steam integration, commercial Steam distribution. Grew from a thin integration layer into a full emulator host:
- Rendering: platform-adaptive (D3D11/DXBC Windows; SDL_GPU/SPIR-V/Vulkan Linux); multi-axis video filter stack (structural filters, two-pass overlay, color effects, motion effects, picture adjustments, video presets)
- Audio: 7-processor SDL3 chain
- UI: in-game + main-menu, keyboard/gamepad nav, 10-language localization
- Achievements: ECDSA-signed; save states
- Ships as Windows x64 + Linux x64 exes; publishes any NES ROM to Steam without modifying the ROM

`BizHawk/`: adapted from BizHawk multi-system emulator, authoritative NES emulation layer. **Frozen vendored dependency**, no proactive upstream sync (NES core is decades-stable). Modify only for a confirmed emulation-accuracy bug or security issue; cherry-pick the fix, never bulk-merge.

## Build & Run Commands

```bash
# Build the full solution
dotnet build NEShim.sln

# Build release
dotnet build NEShim.sln -c Release

# Run tests
dotnet test NEShim.Tests/NEShim.Tests.csproj

# Run a single test
dotnet test NEShim.Tests/NEShim.Tests.csproj --filter "TestName"
```

`net9.0` app, runs natively on Windows x64 + Linux x64 (SDL3 windowing; D3D11 Windows, SDL_GPU/Vulkan Linux). BizHawk lib targets `net8.0`.

### Testing on Proton / Steam Deck — use the publish script, not `dotnet build`

**Never use `dotnet build` output for Proton/native-Linux/Steam Deck perf testing** — local vs. published builds differ significantly (real confusion: local builds looked frame-rate-broken, release didn't). Always `local-publish.ps1` → copy to device; `dotnet build` output is only valid for logic iteration + tests on Windows.

Why (`local-publish.ps1` flags):
- `--self-contained true` — bundles the exact .NET 9 runtime; framework-dependent builds rely on whatever wine-mono/dotnet-wine provides (different GC/scheduler behavior possible).
- `-p:PublishReadyToRun=true` — precompiles IL to native x64, no runtime JIT. JIT is expensive under Proton/Wine: every JIT codegen step calls `VirtualAlloc`/`VirtualProtect`, intercepted/translated by Wine → frame spikes on first entry to each method (ROM load, menu open, achievement unlock, etc.) without R2R.

## Architecture

### NEShim Application Layer (`NEShim/`)
SDL3-based app. `NEShimApp.cs` — orchestrates startup, wires components, owns app lifecycle. `SDL3WindowHost` — SDL3 window + event loop + `MarshalToMainThread` (≈ WinForms `BeginInvoke`). `Program.cs` (entry point): `PlatformDetector.BeginHighResolutionTiming()` → creates `SDL3WindowHost` → `new NEShimApp(sdlHost).Run()`. Layer owns SDK integrations (Steamworks etc.); delegates all emulation to BizHawk.

Key subsystems and their responsibilities:

| `NEShim.Emulation` | BizHawk bridge (`EmulatorHost`), controller adapter, stubs |
| `NEShim.GameLoop` | `EmulationThread` — timing, hotkeys, pause logic |
| `NEShim.Rendering` | `IFrameRenderer` strategy (Windows: `D3D11Renderer` primary / `SDL3HwRenderer` fallback; Linux: `SDL3HwRenderer`), `IMenuSceneProvider` pull interface, `SDL3PaintContext` (cross-platform paint surface — wraps an SDL_Surface for menu/HUD rendering), `SdlSurfaceLoader` (cross-platform image loader using SDL3_image), `FrameBuffer` (double-buffer), `IOverlayRenderer` (platform overlay strategy — `SteamOverlayRenderer` on Windows, also responsible for creating the D3D11 device + swap chain bound to the SDL HWND that the Steam overlay hooks into; `NullOverlayRenderer` on Linux); D3D11 subsystems: `Filters/` (structural DXBC pixel shaders + two-pass overlay via intermediate RT), `MotionEffects/` (`IMotionEffect` strategy — CPU quad-offset effects implement `GetFrameOffset`; shader-backed effects additionally provide `PixelShaderResourceName` and `WriteShaderParams`), `VideoColorFilterMode`, `OverscanMode`, `VideoPreset`, `VideoPresetRegistry` |

### BizHawk Emulation Core (`BizHawk/`)

The core is a faithful port of BizHawk's NES subsystem. Key layers:

**Emulation framework** (`BizHawk/Emulation/Common/`): Interfaces that all emulator cores implement — `IEmulator`, `IStatable`, `ISaveRam`, `IDebuggable`, `IInputPollable`, `IRegionable`, `ISettable<,>`, plus `IEmulatorServiceProvider` for runtime service lookup.

**NES core** (`BizHawk/Emulation/Cores/Consoles/NIntendo/NES/`):
- `NES.cs` — Main orchestrator, implements all the emulation interfaces above
- `NES.Core.cs` — Frame execution loop
- `PPU.cs` — Picture Processing Unit (scanline/sprite rendering)
- `APU.cs` — Audio Processing Unit (Pulse ×2, Triangle, Noise, DMC channels)
- `Boards/` — 150+ cartridge mapper implementations, all extending `NesBoardBase`

**CPU** (`BizHawk/Emulation/Cores/CPUs/MOS 6502/`): Generic `MOS6502X<TLink>` — cycle-accurate 6502 emulator with a disassembler.

**Common utilities** (`BizHawk/Common/`): Checksums (CRC32/MD5/SHA1), bit-manipulation helpers, platform abstractions (Win32/POSIX), and collection/buffer extensions.

### Mapper System
Each NES cartridge type maps to a `NesBoardBase` subclass in `Boards/`. The board handles PRG/CHR bank switching and any on-cartridge hardware. When adding game support, the relevant board is usually the first place to look for emulation bugs.

### Design patterns in use

- **State machine** (`InGameMenu`, `MainMenuScreen`) — both implement `IMenuHost` (explicit interface implementation — keeps its members off each class's own public surface, reachable only through an `IMenuHost`-typed reference) and dispatch via one shared top-level `Screen` enum to a per-screen handler. Two handler shapes coexist behind one `IScreenHandler` interface: menu-specific handlers (`RootHandler`/`MainHandler`, `ConfirmHandler`, `SoundHandler`, `SaveSlotSelectHandler`, `ResumeSlotsHandler`, `ControllerDisconnectedHandler`) stay nested private classes deriving from each menu's own `ScreenHandler` base (full access to the concrete menu, since they touch things `IMenuHost` doesn't expose — `_saveStates`, `Close()`, menu-specific events); the ~11 handlers whose logic is identical between the two menus (`VideoHandler`, `VideoFilterHandler`, `VideoMotionEffectHandler`, `VideoPictureHandler`, `VideoPresetsHandler`, `AudioFilterHandler`, `AudioEqHandler`, `GamepadBindingsHandler`, `KeyboardBindingsHandler`, `LanguageHandler`, `SettingsHandler`) live once in `UI/SharedMenuHandlers/`, deriving from `SharedScreenHandler` (`protected IMenuHost Menu`) instead of either concrete menu — one implementation, constructed by both menus' `BuildHandlers()`. New screen with menu-specific logic = enum value + nested handler class + one `BuildHandlers()` entry (per menu); new screen with identical logic in both menus = enum value + one `SharedScreenHandler` class + one `BuildHandlers()` entry in *each* menu (both construct the same shared class). Rendering always delegated to a paired stateless `*Renderer` (read-only state param). Never mix: no rendering in a state machine, no state mutation in a renderer. `IScreenHandler.GetItemIcon(int) => IntPtr.Zero` virtual; only `LanguageHandler` overrides it (flag `Bitmap`s from `FlagImageLoader`). A new screen expressible as plain-text/slider/icon rows (the common case) needs **no renderer changes at all**: both renderers' item loops already dispatch per-row from `GetSliderData`/`GetItemIcon`/`GetItemValueIcon` into the shared `UI/Controls/` components (see below), so registering the handler is sufficient — the screen renders automatically on both menus. Full recipe, including the rarer case of a genuinely new row shape: gh-pages `architecture.md`, "Adding a new menu screen".
- **Video preset state** — `AppConfig.VideoPreset` (`"None"|"NoFilters"|"LivingRoom"|"Arcade"|"Sharp"|"Phosphor"`) tracks the last-applied preset. `ApplyPreset(VideoPreset)` sets all 8 filter fields atomically (`VideoFilter`, `VideoFilterOverlay`, `VideoColorFilter`, `VideoMotionEffect`, `OverscanMode`, `VideoBrightness`, `VideoContrast`, `VideoSaturation`, `VideoHue`), writes the preset name, fires callbacks, calls `_onConfigSaved()`. `ClearPreset()` → `"None"` ("No Preset" — distinct from the real "No Filters" preset, which actively resets every setting), called from every individual-setting handler (`VideoFilterHandler.Activate`, `VideoMotionEffectHandler.Activate`, `VideoPictureHandler.Activate`, `VideoHandler.CycleOverlay`/`.Activate`, `AdjustPicture`, `ResetPicture`). Displayed via `MenuBindingHelpers.VideoPresetDisplayName(name, localization)`. `VideoPresetsHandler` (`Screen.VideoPresets`) lists `VideoPresetRegistry.All` (idx 1–5, now including "No Filters") + "No Preset" (idx 0), checkmark when active. New preset = `VideoPresetRegistry.All` entry + a `PresetName`/`VideoPresetDisplayName` switch case — no new handler class.
- **Strategy + Chain of Responsibility** (language resolution) — `ILanguageResolver` = strategy; `ChainedLanguageResolver` tries `SteamLanguageResolver` → `CultureInfoLanguageResolver`. `NEShimApp.ResolveLanguage()`: explicit `config.Language` wins; `"Auto"` → chain. Both resolvers log every decision. `SteamLanguageResolver` normalizes via `LanguageRegistry.FindBySteamCode` (handles `koreana`→`korean`, `brazilian`→`portuguese`; returns null for unsupported e.g. `tchinese`, falls through). `CultureInfoLanguageResolver.FindByCulture`: exact `culture.Name` first, then `TwoLetterISOLanguageName`. Simplified Chinese uses explicit prefixes (`zh-CN`, `zh-SG`, `zh-Hans`) not bare `zh`, since `zh-Hant`/`zh-TW` (Traditional) share the two-letter code.
- **Live language switching** — `InGameMenu`/`MainMenuScreen`.`UpdateLocalization(LocalizationData)` rebuilds binding arrays + handlers in-place on language change. `NEShimApp.OnLanguageChanged`: save config → reload localization → `UpdateLocalization` on both menus → mark overlay dirty.
- **Observer (events)** — upward comms via C# events (`NewGameChosen`, `ResumeChosen`, `Opened`, `Closed`), wired in `NEShimApp.InitializeEmulator()`.
- **Double-buffer** — `FrameBuffer`: back buffer (emulation thread writes) / front buffer (paint thread reads), `Swap()` under `SpinLock`. Never read the back buffer from the paint thread or write the front buffer from the emulation thread.
- **Pause flags** — `EmulationThread.PauseReasons` `[Flags]` enum; any non-zero blocks the loop on a `ManualResetEventSlim`. Always `SetPauseReason(reason, active)`, never set bits directly (handles the CAS loop + audio mute side-effect).
- **Stateless renderer** — `MainMenuRenderer`/`MenuRenderer`: `internal static`, single `Draw(SDL3PaintContext, SDL.Rect, <StateType>)` entry, pure/no side-effects. No font/surface caching in these classes — use `SDL3FontCache`. Per-row/per-element drawing (item rows, sliders, the controller diagram, panel chrome) is delegated to `UI/Controls/` (below) — each renderer's own `Draw`/`DrawPanel`/`PanelMetrics` retains only its menu-specific panel layout and orchestration (main-vs-sub-panel dispatch, disconnect screen, rebind-prompt shape — these differ genuinely between the two menus and are not unified).
- **Composable presentational components** (`UI/Controls/`) — `ItemRowControl`, `IconRowControl`, `SliderControl`, `ControllerDiagramControl`, `PanelFrameControl`: `internal static` classes shared by both `MenuRenderer` and `MainMenuRenderer`, replacing what was previously five near-duplicated private methods per file (one pair, `DrawControllerSprite`/`DrawItemRow`, was byte-identical between the two files; the color palettes feeding them had already silently drifted apart in one case — `SelectedBg` differed by a few RGB values between the two menus before this extraction). Each takes only plain data (props) — colors, rects, scale, text — never a menu-type reference, so a component composes into either renderer, or a future one, unchanged; this mirrors a framework's presentational/"dumb" component (props in, draw out) versus each renderer's own `Draw`/`DrawPanel`, which plays the container role (reads menu state, resolves colors/text, delegates row drawing). Every component with real layout math splits a `Draw(SDL3PaintContext, ...)` method (SDL-dependent, untested per the renderer-testing rule below) from a pure `ComputeLayout`/`ComputeGeometry` method returning a small `readonly record struct` (`ItemRowLayout`, `IconRowLayout`, `ControllerDiagramLayout`, `SliderGeometry`) — unit-tested in `NEShim.Tests/UI/Controls/`, mirroring the pre-existing `ComputeDisplayRect`/`ComputeCoverSrcFRect` convention. `SliderControl` unifies what was previously an asymmetric extraction (`MainMenuRenderer.ComputeSliderGeometry` was already extracted and tested; `MenuRenderer`'s equivalent was inline and had zero test coverage) — the in-game menu's slider geometry is now tested for the first time. `IconRowControl.Draw` deliberately has no `enabled`/dim-color branch of its own (unlike the two private methods it replaced): both call sites only ever invoke it for the Language screen's flag rows, which are always enabled by design, so the branch was dead in both original files — callers resolve the final `textColor` before calling, once, matching how every other row type already worked. Panel-level sizing constants (`ItemH`, `PanelHeaderH`, etc.) stay in each renderer, not lifted into `Controls/` — the two menus' differing item heights (38 vs 42) and header heights are a deliberate visual-density difference, not duplication.
- **Pull scene interface** (`IMenuSceneProvider`) — renderer doesn't know the active UI scene; calls `GetActiveScenePainter()` each frame. `NEShimApp` implements it: returns a paint delegate (`Action<SDL3PaintContext, SDL.Rect>`) for the current scene, `null` during gameplay (zero hot-path overhead). Invoked in the overlay pass before FPS/toast/achievement overlays (scene sits under the HUD). Never add scene-detection logic to the renderer.
- **Menu input interface** (`IMenuInputTarget`) — `EmulationThread` dispatches gamepad nav without knowing `NEShimApp` directly: calls `IsWaitingForGamepadButton`, `HandleGamepadNav`, `HandleGamepadButtonPress`. `NEShimApp` implements it, routes to the active state machine. Explicit interface impls (e.g. `void UI.IMenuInputTarget.HandleGamepadNav(...)`) avoid CS0051 from the internal `MenuNavInput` type appearing in the signature.
- **Memento** (save states) — `SaveStateManager` wraps BizHawk's `IStatable`: the emulator core is the originator (`SaveStateBinary`/`LoadStateBinary`), the byte stream is the memento, `SaveStateManager` is the caretaker (8 named slot files + `SlotMeta` JSON timestamp, plus the auto-save slot). Already the correct shape, just not previously named as this pattern.
- **Explicit interface implementation for narrow, single-purpose contracts** — `IMenuHost` (`InGameMenu`/`MainMenuScreen`, consumed only by the ~11 `SharedScreenHandler`-derived handlers in `UI/SharedMenuHandlers/`) follows the same idiom as `IMenuInputTarget` above: implemented explicitly so the interface's members are reachable only through an `IMenuHost`-typed reference, adding zero surface to either menu's own public API. `IScreenHandler` is the matching common contract both menu-specific nested `ScreenHandler` base classes and the shared `SharedScreenHandler` base implement, so both handler shapes coexist in one `Dictionary<Screen, IScreenHandler>` per menu.

### Rendering architecture: Windows vs Linux

**Windows (D3D11):** primary path, built on the `SteamOverlayRenderer`'s device/swap chain; falls back to `SDL3HwRenderer` if D3D11 init fails.

**Linux (SDL_GPU):** `RendererFactory.cs` creates an SDL_GPU renderer backed by Vulkan — this is the same `SDL3HwRenderer` class Windows falls back to, so most of the pipeline (frame delivery, overlay compositing, render pass model, filter/motion-effect extension points, device loss recovery — see "Shared rendering pipeline" below) is genuinely shared, not Windows-only. `NullOverlayRenderer` used (Steam's overlay injected via `LD_PRELOAD` on Linux; no swap chain hook needed). `PlatformDetector.IsD3D11Active` is `false` on Linux; D3D11-specific features (see "D3D11-specific rendering details" below) aren't offered in menus.

**Linux SDL_GPU bootstrapping gotchas** (from a real native Linux/Steam Deck/WSL2 segfault investigation, July 2026 — kept so this ground isn't re-covered):
- **Root cause: `SDL_CreateGPURenderer` argument order.** Real signature is `(SDL_GPUDevice *device, SDL_Window *window)` — device first, no shader-format parameter. The bug passed the window as `device` and a `GPUShaderFormat` enum's raw int (`SPIRV = 2`) as `window`, corrupting SDL's internal renderer bookkeeping (crash inside `SDL_RemoveWindowRenderer`) instead of returning `NULL`. Reproduced identically on Steam Deck and WSL2, proving it was a wrong function call, not a driver/environment issue. `SDL3HwRenderer.TryCreateGpuRenderer` now passes `IntPtr.Zero` for `device` and the real window for `window`. **Lesson: check a native library's documented signature before investigating environment differences.**
- **Ruled out, don't re-litigate:** X11-vs-Wayland driver choice and Steam-Deck-specific branching — the crash reproduced identically under both, so `ConfigureVideoDriverForSteamOverlay()` unconditionally forces `x11` on Linux again, no conditions.
- **`SDL_WINDOW_VULKAN`** is required at `SDL_CreateWindow` time for Vulkan surface/GPU-renderer use (`SDL3WindowBuilder.ComputeWindowFlags`) — Linux-only, since `SDL_CreateWindow` itself fails without a Vulkan driver present, and Windows' D3D11 path needs no Vulkan surface.
- **Window shown before renderer construction, Linux only** (`NEShimApp.InitializeWindowAndRenderer`) — a Wayland/XWayland surface-mapping precaution, not confirmed necessary for the crash above, kept since there's no isolated test without it.
- **`SdlGpuRenderState`'s hand-rolled `SDL_GPURenderStateCreateInfo` struct had a fabricated field set** (bogus "vertex" sampler/storage counts, no pointer fields, a nonexistent `NumFragmentUniformBuffers`) that didn't match the real layout (`fragment_shader, num_sampler_bindings, sampler_bindings, num_storage_textures, storage_textures, num_storage_buffers, storage_buffers, props` — verified against the SDL3 header-derived field list). Fixed regardless as a real correctness bug, but turned out not to be the cause of the symptom below — creating the render state with the wrong struct didn't itself crash.
- **Root cause of "any shader-based filter blacks out all rendering": vertex/fragment interface mismatch, not the struct above.** `SDL_CreateGPURenderState` replaces only the fragment stage — the vertex stage stays SDL's own built-in one, whose real output interface (confirmed against SDL's own shipped test shader, `testgpurender_effects_CRT.frag.hlsl`) is `COLOR0` (vec4) at location 0, `TEXCOORD0` (vec2) at location 1. Every filter/motion-effect/picture-adjust fragment shader's `PSInput` declared only `TEXCOORD0` at location 0, colliding with the real vertex shader's vec4 output there. This doesn't fail at shader/render-state creation — `vkCreateGraphicsPipelines` compiles pipelines lazily, so it only surfaces (`VUID-RuntimeSpirv-maintenance4-06817`) the first time a shader-based filter is actually drawn, i.e. exactly when gameplay starts (menu navigation and filter *selection* never trigger a real NES-frame draw, so they always looked fine). The failed pipeline build then blacked out all rendering (in-game menu included, sharing the same `SDL_Renderer`) and froze input if `Present` blocked waiting on it, while audio (separate subsystem) kept running — reproduced identically on WSL2. Invisible without Vulkan validation layers (`VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`), since without them the driver just silently hangs instead of reporting the interface error — **reach for validation layers first for any silent Vulkan black-screen/hang, rather than reasoning about it from source alone.** Fixed in every affected `Vulkan/*.ps.hlsl` (`Jinc2`, `CrtScanlines`, `CrtPhosphor`, `CrtScreen`, `NtscComposite`, `Xbr`, `MagneticDistortion`, `PictureAdjust` — not `PhosphorPersistence.ps.hlsl`/`Passthrough.*.hlsl`, which their own doc comments already flag as unused by the `SDL_CreateGPURenderState` path): `PSInput` reordered to `COLOR0` first, `TEXCOORD0` second, output multiplied by `input.color` so DXC doesn't optimize the now-required interface variable away (a no-op today — nothing applies `SDL_SetTextureColorMod`/`AlphaMod` to these draws — but keeps the shader correct if that ever changes). Recompiled via `dxc.exe` from the `Microsoft.Direct3D.DXC` NuGet package; D3D11's `Dx11/*.hlsl` shaders are untouched and unaffected — D3D11 binds its own real custom vertex shader (`Dx11/Passthrough.vs.hlsl`) and never goes through this SDL API at all.

**Post-launch Linux rendering fixes** (same session, after the app first ran on native Linux — latent bugs never previously exercised):
- **Stale cached texture on surface reuse.** `SDL3PaintContext`'s `_textureCache` is keyed by surface `IntPtr`; destroying a surface without calling `InvalidateTexture` first lets a later surface reusing the same freed address silently inherit the stale texture. `GameCarouselScreen` already handled this via an `onSurfaceDisposing` callback; `LogoScreen`/`MainMenuScreen` didn't — the logo's freed surface got reused by the main menu background's allocation, rendering a stretched logo instead of the real background. Both now take the same `onSurfaceDisposing` callback, wired the same way in `NEShimApp`. Any future SDL-surface-owning screen needs this too.
- **No Linux font path.** `SDL3FontCache` only ever checked `%WINDIR%\Fonts` — every lookup failed silently on Linux, so no text rendered. Added `LinuxSansCandidateFilenames` (DejaVu Sans, then Liberation Sans) located via `FindLinuxFontFile`'s recursive search under `/usr/share/fonts`/`/usr/local/share/fonts` (Arch/SteamOS and Debian/WSL2 lay out font packages differently, so a search beats a guessed path). CJK fallback gets an analogous best-effort Noto Sans CJK path.
- **`FontSizeCorrection = 0.75f`** (`SDL3FontCache`) — the existing `96/72 * 1.4` GDI+/FreeType factor, combined with `MenuScale.Scale` (which legitimately grows past 1.0 at large fullscreen resolutions — don't cap it, see `MenuScale`'s own doc comment), read too large on both platforms at 1920×1080. Applied unconditionally on both platforms; empirically tuned, re-tune if needed.
- **`PanelW` vs `ScaledPanelW`** (`MenuRenderConstants`) — `PanelW` only scaled with `MenuScale.Scale` on Steam Deck; on desktop it stayed fixed-width regardless of resolution, so at large fullscreen resolutions the binding screens' item-list text (which does scale) outgrew its column and bled into the controller diagram. Fix is scoped, not universal: narrower panels (Settings, etc.) are meant to stay skinnier than binding-screen panels, so only `FullPanelW`/`ControllerAreaW` (the two binding screens, in `MainMenuRenderer`/`MenuRenderer`) use the new always-scaling `ScaledPanelW`; every other panel keeps `PanelW`'s original Steam-Deck-only behavior.

### Shared rendering pipeline (D3D11 + SDL_GPU)

Applies to both `D3D11Renderer` (Windows) and `SDL3HwRenderer` (Linux always; Windows fallback) unless a bullet says otherwise. `SDL3HwRenderer` supports the full feature set: structural filters (SPIR-V), color effects, picture adjust, all 4 motion effects (CRT Jitter, Scanline Bob, Magnetic Distortion, PhosphorPersistence), Video Overlay (2nd-pass slot).

- **Frame delivery**: emulation thread batches `UploadFrame`+`Tick` in one marshal call to main thread → Present fires right after texture ready, no clock drift. `OnIdle` (SDL loop) calls `SteamManager.Tick()` + `Renderer.Tick` while emulation paused, to keep the Steam overlay hook alive.
- **Overlay/HUD compositing**: each renderer keeps its own overlay texture sized to match the swap chain/target (D3D11: a separate BGRA texture; `SDL3HwRenderer`: its own equivalent — see its doc comment for exact fields). `DrawOverlay()`: if scene (`IMenuSceneProvider.GetActiveScenePainter()`) or transient HUD active → `RenderOverlayBitmap()` paints CPU-side `SDL3PaintContext` (scene then HUD) → upload → alpha-blend over the NES frame. `MarkOverlayDirty()` forces repaint next `DrawAndPresent`/tick (called on menu-state change). Scene painter re-invoked every frame while active (cursor move doesn't call `MarkOverlayDirty`).
- **Pixel format**: BizHawk `IVideoProvider` → `int[]` of `0xAARRGGBB`; little-endian bytes = `[B,G,R,A]` = `B8G8R8A8_UNorm` directly, no swap (D3D11 side). `UploadFrame` row copy always via `MappedSubresource.RowPitch` on D3D11 (DXVK may widen row alignment).
- **No mouse input** anywhere in menus — `SDL.HideCursor()` once at startup, never shown again. Nav is keyboard/gamepad only.
- **`EmulationThread` decoupling**: takes `Action<Action> _marshalToMainThread` (SDL marshal delegate) + `IMenuInputTarget _menuInput` (gamepad dispatch, = `NEShimApp`). `NEShimApp` implements `IMenuInputTarget` explicitly (avoid CS0051).
- **Device loss recovery**: both renderers implement `IFrameRenderer.DeviceLost`; `NEShimApp.OnRendererDeviceLost` (subscribed at initial creation + inside its own recovery) handles both the same, platform-agnostic way: `PauseReasons.DeviceLost` → dispose renderer+overlay → recreate via `RendererFactory.Create`/`OverlayRendererFactory.Create` (`SetMenuSceneProvider(this)` again) → clear pause. Detection differs per platform API: `D3D11Renderer.PresentAndCheckResult` fires `DeviceLost` immediately on `DXGI_ERROR_DEVICE_REMOVED`/`_RESET` (structured codes, no debounce needed). `SDL3HwRenderer.PresentAndCheckDeviceLost` has no structured signal (`SDL.RenderPresent` → bool + free-form `SDL.GetError()`, can't distinguish real loss from a benign resize-driven swapchain race) → needs `DeviceLostFailureThreshold` (3) *consecutive* failed presents before firing; counter resets on `Resize()` so resize's own transient failures don't accumulate.
- **Render pass model** (`DrawAndPresent`/`DrawNesFrame`, 1–4 passes depending on active effects — D3D11 member names shown; `SDL3HwRenderer` mirrors the exact same stage-ordering/colour-grade-deferral with its own fields, see its doc comment). Which stage applies the colour grade — the decision both renderers used to re-derive independently, once in D3D11 as nested branch structure and once in SDL as explicit booleans — is now one shared pure function, `RenderPassPlanner.ColorApplyingStage(hasOverlay, hasMotionEffectShader)`, unit-tested with no GPU dependency (`RenderPassPlannerTests.cs`). Both renderers compute it once per frame and compare against it instead of hand-deriving `colorMode=0`-vs-real per call site:
  - Single pass (no overlay, no shader motion effect): structural filter → backbuffer directly (`DrawNesQuad`).
  - Two passes (overlay, no shader ME): structural → `_overlayRt` (letterbox-sized, `colorMode=0`) → overlay filter reads `_overlayRt` → backbuffer (real `colorMode`).
  - Two passes (no overlay, shader ME active): structural → `_motionEffectRt` (letterbox-sized, `colorMode=0`) → `DrawMotionEffectToBackbuffer()` (ME shader reads `_motionEffectRt`) → backbuffer.
  - Three passes (both): structural → `_overlayRt`; overlay → `_motionEffectRt` (`colorMode=0`); ME shader → backbuffer.
  - +1 picture-adjust pass (any of Brightness/Contrast/Saturation/Hue non-zero): prior passes write `_pictureAdjustRt` (viewport-sized) instead of backbuffer; `DrawPictureAdjust()` reads it → backbuffer. Own independent `b0` (`{brightness,contrast,saturation,hue}`), written directly, not via `WriteBaseParams`. All 4 at config defaults (0) → RT not allocated, pass skipped.
  - PhosphorPersistence (SDL_GPU path only — D3D11 doesn't need this workaround): no SPIR-V shader — `SDL_GPURenderState` binds only 1 sampler/draw (no 2nd-slot API like D3D11's `PSSetShaderResource` slot 1) → `max(current, previous*decay)` reproduced via 2 single-sampler draws into a ping-pong accumulation texture (`SDL_ComposeCustomBlendMode` Maximum op + `SetTextureColorModFloat` for decay) — GPU fixed-function blending, no CPU pixel work.
- **Adding a video filter (structural)** — 7 places, both renderer paths: (1) enum value in `VideoFilterMode` + update `D3D11Supported`; (2) `.ps.hlsl` in `Shaders/Dx11/` (`#include "ColorGrade.hlsli"`, call `ApplyColorGrade`, 4-float `cbuffer FilterParams`); (3) `ID3D11Filter` impl in `Filters/Dx11/`; (4) case in `D3D11FilterFactory.Create`; (5) same HLSL → SPIR-V (`.ps.spv` in `Shaders/Vulkan/`); (6) `ISdlFilter` impl in `Filters/SDL/` (`PixelShaderResourceName`, `WriteUniformData`, `NumFragmentSamplers`, `NumFragmentUniformBuffers`); (7) case in `SdlFilterFactory.Create`. Register `.cso`+`.spv` as `<EmbeddedResource>` in `NEShim.csproj`. `OverlaySupported` entry only if it can run as D3D11 2nd-pass overlay. `null` from `PixelShaderResourceName` (both interfaces) reuses the passthrough shader.
- **Adding a motion effect** — implement `IMotionEffect` under `MotionEffects/`. CPU quad-offset effect: `GetFrameOffset`+`NotifyLayout` only (returned `(dx,dy)` = clip-space NES-quad offset, no extra pass); register in `MotionEffectFactory.Create` (D3D11) + `SdlMotionEffectFactory.Create` (SDL) — same impl both paths. Shader-backed effect: also return non-null `PixelShaderResourceName` (D3D11) + implement `ISdlMotionEffect` (adds `SpvResourceName`, `NumFragmentSamplers`, `NumFragmentUniformBuffers`); renderer allocates an intermediate RT + dedicated shader pass. Add `.hlsl`+`.cso` (D3D11) and `.spv` (SDL), register in `NEShim.csproj` (pattern: `MagneticDistortion`). Add `Parse()`/`DisplayName()` cases in `VideoMotionEffectModeParser`. Temporal effects needing 2 simultaneous samplers (ping-pong) can't be expressed via `SDL_GPURenderState` — return `NoneMotionEffect` (+ log entry) from `SdlMotionEffectFactory.Create`.
- **Slow-frame timing log**: `enableLogging` → `EmulationThread` logs any frame >14ms total work (2.67ms below the 16.67ms budget), broken into `input`/`runFrame`/`video`/`audio`. First place to check for FPS regressions. Debug builds: `runFrame` 17–30ms is normal (unoptimised BizHawk JIT), not a bug. Always use Release for perf testing.

`SteamAPI.RestartAppIfNecessary(appId)` — called in `Program.Main` before `new SDL3WindowHost(...)`. Reads App ID from `steam_appid.txt`. Not launched via Steam → returns `true`, process exits, Steam relaunches with overlay DLL injected (Windows: `GameOverlayRenderer64.dll`; Linux: `steamoverlayvulkanlayer.so` via `LD_PRELOAD`).

### D3D11-specific rendering details (Windows)

`SteamOverlayRenderer` creates D3D11 device + swap chain (`SwapEffect.FlipDiscard` — required for DXVK/Proton) bound to HWND from `SDL3WindowHost.Handle`. `RendererFactory.Windows.cs` tries `D3D11Renderer`; falls back to `SDL3HwRenderer` if overlay device/swap chain is null or the ctor throws.

- **D3D11 = primary path for everything**, not just NES frames — logo, main menu, in-game menu, all HUD overlays (FPS/toasts/achievements) composed by `D3D11Renderer`. `SDL3HwRenderer` takes over ALL rendering (not just NES) when D3D11 unavailable.
- `SteamOverlayRenderer` init must be **after** `SetWindowMode` (swap chain must match final window size); `D3D11Renderer` constructed right after. `SDL3WindowHost.Resized` → `D3D11Renderer.Resize()` → `ResizeBuffers` + recreate RTV.
- **`IsD3D11Active`** set once at startup, after `D3D11Renderer` is (or isn't) constructed; `IsSdlGpuRendererActive` set analogously when `SDL3HwRenderer` inits via `SDL_CreateGPURenderer` (vs. plain `SDL_CreateRenderer` fallback). In-game Video menu's extended 9-item set (Presets/Overlay/Motion Effect/Picture + base 5) gates on `SupportsAdvancedVideoFeatures` (`IsD3D11Active || IsSdlGpuRendererActive`), not `IsD3D11Active` alone — SDL_GPU path supports the full set too. Only the bare `SDL_CreateRenderer` fallback (no GPU device at all — needs both D3D11 AND `SDL_CreateGPURenderer` to fail, extremely rare) shows the reduced 5-item menu (Window/Filter/Overscan/FPS/Back).
- `IntermediateRenderTarget` (private nested, `D3D11Renderer`): groups `ID3D11Texture2D`+RTV+SRV+dimensions. `Sync(device,w,h)`: create/dispose to match, early-exit if size unchanged. `SyncOverlayRt()`/`SyncMotionEffectRt()`/`SyncPictureAdjustRt()`: thin wrappers, condition-guarded dims (0 when inactive), log on creation. Called from `Resize`; `SyncMotionEffectRt` also from `UpdateLetterboxRect` (ME intermediate tracks letterbox changes from filter PAR diffs); `SyncPictureAdjustRt` also on picture-setting change. Overlay slot: `CrtScanlines`/`CrtPhosphor`/`CrtScreen` only (composable on an already-scaled frame). Menu blocks selecting the same filter for primary+overlay (`IsItemEnabled`); picking a primary filter matching the current overlay clears the overlay to `None`.
- **Cbuffer layout fixed**: `b0` = exactly 4 floats `{param0, param1, param2, colorMode}`. Structural filters use slots [0..2] via `WriteBaseParams()`; renderer owns slot [3] (colorMode), always writes it. No filter gets a 2nd constant buffer — if one genuinely needs >3 config floats, revisit this rule explicitly, don't work around it silently. Exception: `PictureAdjust.ps` is a fully separate pass with its own dedicated `b0` (`{brightness, contrast, saturation, hue}`), written directly by the renderer; the structural-filter cbuffer rule doesn't apply to it.
- **Proton/DXVK notes**:
  - `SwapEffect.FlipDiscard` required — legacy `Discard` uses a slower DXVK blit path.
  - `UploadFrame` row-copies via `RowPitch` — DXVK aligns rows for Vulkan.
  - DXBC passthrough shaders compile to SPIR-V on first Proton launch (cached in Steam shader cache), near-instant (trivial shaders).
  - `local-publish.ps1`, not raw `dotnet build`, for Proton perf testing.

### Third-party native dependency pinning

Both dependencies below pair a managed wrapper with a platform-specific native binary — the same class of bug (managed/native version skew) has bitten this project for real on both, so they're grouped here rather than under either Windows or Linux specifically.

#### Steamworks.NET version pinning

Do **not** upgrade Steamworks.NET via NuGet — the NuGet package tops at 2024.8.0 (SDK 1.60), which is incompatible with SDK 1.63+. Use the GitHub releases zip instead:

- **Steamworks.NET**: 2025.163.0 — local DLL at `NEShim/lib/Steamworks.NET.dll`
- **steam_api64.dll**: **not stored in the repository** (Valve SDK license). At packaging time, copy it from the Steamworks.NET GitHub release zip into the output directory alongside the exe — it is matched to the wrapper version. Do not source it separately from the Steamworks SDK partner dashboard, and do not commit it to source control.
- **Linux native lib naming gotcha**: the wrapper's `DllImport` targets are compiled against the literal name `steam_api64` (confirmed via binary inspection of `Steamworks.NET.dll` — no other `steam_api*` string appears), which .NET's Linux native-library resolution maps to `libsteam_api64.so` — but the Steamworks.NET release zip ships the Linux redistributable as `libsteam_api.so`. Deploying it under that zip-default name causes `SteamAPI.Init()` to throw internally (native library not found); `SteamManager.Initialize`'s try/catch swallows this, logs `[Steam] Init failed: ...`, and sets `IsAvailable = false` — the app keeps running with no crash or on-screen error, but every Steam feature (achievements, overlay, DLC ownership) is silently disabled (reproduced during native Linux/Steam Deck testing, July 2026). It must be **renamed to `libsteam_api64.so`** in the output directory.
- Reference in csproj: `<Reference Include="Steamworks.NET"><HintPath>lib\Steamworks.NET.dll</HintPath></Reference>`

SDK 1.61+ has the Steam client sync stats before the game process launches, so stats are already in the local cache when `SteamAPI_Init` returns. `SteamUserStats.RequestCurrentStats()` still exists in Steamworks.NET 2025.x but is marked obsolete and always returns `true` without doing anything — do not call it.

#### SDL3-CS version pinning

Every `SDL3-CS*` `PackageReference` (`SDL3-CS`, `SDL3-CS.Windows`, `SDL3-CS.Linux`, `SDL3-CS.MacOS`) must be pinned to the **exact same version**, never floating (`3.*`) on some while pinned on others — the managed bindings are one shared package, native bindings are per-platform, and NuGet resolves floating references independently, letting them silently drift apart. This happened for real (Steam Deck + WSL2, July 2026, discovered while investigating the `SDL_CreateGPURenderer` segfault above — that crash's actual cause was the argument order, not this): `SDL3-CS` had floated to `3.4.12.6` while `SDL3-CS.Linux` stayed pinned at `3.4.12`, six releases behind. Two of the skipped patches changed renderer P/Invoke signatures upstream (`SDL_SetRenderViewport`, `SDL_RenderTextureAffine`) — not the cause of that crash, but a real latent ABI-mismatch risk. Windows avoided it only by coincidence: `SDL3-CS.Windows` also floats and happened to track the same releases.

All four are pinned to **`3.4.12.1`** — the newest version listed for all of them (`3.4.12.6` is unlisted/broken for some, notably Linux). When upgrading, bump every platform variant together in the same change and confirm each is actually listed on NuGet — don't trust `3.*` to keep them in sync. The `.TTF`/`.Image` sub-packages bundle their own self-contained managed+native pair, independent of the base `SDL3-CS` assembly, so they aren't subject to this skew and can keep floating.

### Coding conventions (NEShim layer only)

- **Naming**: `PascalCase` for types, methods, properties, and events; `_camelCase` for private fields; `camelCase` for locals and parameters.
- **Nullability**: Enable nullable reference types (`<Nullable>enable</Nullable>`). Use `?` annotations throughout. Avoid `!` (null-forgiving) except at genuine interop boundaries.
- **Method length**: Keep methods under ~30 lines. Extract named helpers rather than adding comments that describe blocks.
- **One responsibility per class**: State machines hold state and drive transitions; renderers draw; managers own lifecycle and I/O. Do not mix these.
- **No magic numbers**: Give all frame dimensions, timing constants, and UI sizes a named `const` or `static readonly` in the class that owns them.
- **Dispose discipline**: Every `IDisposable` created inside a method must be in a `using` declaration or `using` block. Classes that own SDL surfaces, audio, or host resources must implement `IDisposable` and be disposed in `NEShimApp.Shutdown()`.
- **Thread safety**: Emulation thread and main thread share `_pauseReasonBits` (volatile `int` + CAS) and `FrameBuffer` (SpinLock). All other mutable state is owned by one thread. Use `MarshalToMainThread` (the SDL3 marshal queue delegate from `SDL3WindowHost`) to marshal work to the main thread from the emulation thread — never call SDL functions directly from the emulation thread.
- **One class per file**: each top-level class, interface, enum, or record gets its own `.cs` file named after the type. Acceptable exceptions are small private helper types that are tightly coupled to a single containing class (e.g., a `ScreenHandler` subclass nested inside a state machine) — these may stay in the same file as their owner. Do not add a second public or internal top-level type to an existing file.
- **No `#if` preprocessor directives**: treat `#if` / `#elif` / `#else` as a last resort. Prefer MSBuild `<Compile Remove>` with `Condition` attributes on `<ItemGroup>` to exclude platform-specific files entirely, and `.Platform.cs` / `.Windows.cs` sibling files that define the same class for each target. `#if` is acceptable only where file-level exclusion is genuinely impractical (e.g., a single expression inside a file that is otherwise identical across platforms). Never use `#if` for feature flags or debug-only paths — use runtime checks (`OperatingSystem.IsWindows()`, config values) instead. **Platform `Condition` attributes must key on `$(RuntimeIdentifier)`, never bare `$(OS)`** — `NEShim.csproj` computes a `$(_TargetsWindows)` property once (RID-prefix check, falling back to the host OS only when `RuntimeIdentifier` is empty) and every platform-file/package condition reads that instead. `$(OS)` reflects the *build machine's* OS, not the publish target: `dotnet publish -r linux-x64` run on Windows (exactly what `local-publish.ps1` does, since it's a PowerShell script) would otherwise still evaluate `'$(OS)' == 'Windows_NT'` as true, silently compiling the D3D11/Vortice stack into a "linux-x64" output while omitting the Linux SDL3 native bundles entirely — a build that can't start on Linux at all. This was a real, reproduced bug (verified via an actual cross-published output missing every `libSDL3*.so`), not a theoretical one.
- **Don't modify BizHawk source** unless fixing a direct compatibility issue (emulation accuracy bug or confirmed security fix). Prefer adapter/wrapper classes in `NEShim/Emulation/` to bridge BizHawk interfaces. See the upstream sync policy in "What This Project Is" above.

## Testing

### Libraries and tooling
- **NUnit** — test framework. Use `[TestFixture]`, `[Test]`, `[SetUp]`, `[TearDown]`. Prefer `Assert.That(actual, Is.EqualTo(expected))` constraint syntax over classic assertions.
- **NSubstitute** — mocking library. Add via NuGet (`NSubstitute`). Do not introduce a second mocking library.
- Keep attributes lightweight: avoid `[Category]`, `[Description]`, `[Author]`, and other decorative metadata unless a specific CI filtering need requires them.

### Structure — mirror the SUT
Each class under test gets exactly one test class, in a file that mirrors the source path:

```
NEShim/UI/InGameMenu.cs                          →  NEShim.Tests/UI/InGameMenuTests.cs
NEShim/Achievements/AchievementManager.cs        →  NEShim.Tests/Achievements/AchievementManagerTests.cs
NEShim/Saves/SaveStateManager.cs                 →  NEShim.Tests/Integration/SaveStateManagerTests.cs
```

The last example illustrates that classes with I/O dependencies land in `Integration/` rather than mirroring the source folder directly.

If a source class is not worth testing in isolation (e.g., a pure data record, a stateless renderer), no test class is required.

### Unit test rules
- **No boundary crossing.** A unit test must not touch the file system, audio devices, the Windows registry, network, or any external process. Anything that does is an integration test, not a unit test.
- **Mock dependencies at the boundary.** Use `Substitute.For<T>()` for interfaces and abstract classes that would otherwise pull in I/O or heavy subsystems. Pass substitutes through the constructor (prefer constructor injection over property injection). Verify only interactions that matter to the behaviour under test — do not assert on every call.
- **Do not over-mock.** Concrete collaborators with no I/O side-effects (plain data objects, pure value computations) should be used directly, not mocked. A test that mocks everything except the SUT is testing nothing.
- **Avoid test globals.** Shared `static` state and class-level fields shared across tests make failures hard to diagnose. Initialise the SUT and its substitutes in `[SetUp]` so each test gets a fresh instance. The only acceptable class-level fields are `readonly` constants or substitute / SUT fields initialised in `[SetUp]`.
- **One behaviour per test.** Each `[Test]` method asserts one logical outcome. Name tests in the form `MethodName_Condition_ExpectedOutcome`.

### Boundary-crossing (integration) tests
Tests that must cross a boundary — file system, real audio device, BizHawk core execution — are allowed only when the behaviour cannot be verified any other way. They must live in a separate location:

- **Same project, separate folder** if the test count is small: `NEShim.Tests/Integration/`
- **Separate project** (`NEShim.IntegrationTests/`) if the suite grows or requires different setup (e.g., a real ROM file, elevated permissions).

Never place a boundary-crossing test alongside unit tests. CI should be able to run unit tests alone (`--filter "TestCategory!=Integration"`) without external dependencies.

### Key BizHawk Dependencies
- `CommunityToolkit.HighPerformance` — SIMD/span performance helpers
- `Newtonsoft.Json` — settings serialization

## Multi-Game Mode

Default publish = single-game: one `config.json` + one ROM next to the exe. **Multi-game mode = a second, additive publish path on the same binary** — one exe hosts N games, picked at runtime via a carousel. Never changes single-game behavior; activates only under an explicit opt-in signal. Steam DLC is optional per game, not required by multi-game mode itself (`SteamDlcAppId = 0` default → always shows) — a whole library can ship bundled with zero DLC depots, or mix bundled + paid-DLC games in one install.

- **Detection**: `MultiGameMode.IsActive` (`MultiGameMode.cs`) = `true` when `games/multigame.json` exists next to the exe (a dedicated manifest, not content-scanning) — needed since on a fresh install `games/` may not exist yet if Steam hasn't finished downloading DLC; detection must not depend on DLC content being present. `games/multigame.json` doubles as the *shell config* (`AppConfig` via `ConfigLoader.LoadFrom`) — drives window mode/language/`NoLogo` for the pre-selection carousel period.
- **Per-game layout**: each game in its own `games/<gameId>/` (ROM, `config.json`, `achievements.json`, artwork) under the base install dir. `steam_appid.txt`/`game_actions_<appid>.vdf` stay singular/app-wide — one Steam base App ID, one process. Game's own `steamDlcAppId` set → folder is also a **Steam DLC depot**, mounted only once owned/downloaded; ownership checked at scan time (`SteamApps.BIsDlcInstalled` via `SteamDlcManager.IsOwned`/`FilterOwned`). `SteamDlcAppId = 0` (default) or no live Steam session (`SteamManager.IsAvailable == false`) → shown unconditionally (dev/test without real entitlements; also the supported all-bundled-library pattern). One build can freely mix bundled + paid-DLC games.
- **DLC ownership anti-tamper** (`AppConfig.GameDlcAppIds`/`GameDlcAppIdsSignature`, `DlcMapSigner`, `GameScanner.Scan`): each game's `config.json` (incl. `steamDlcAppId`) lives in its own player-editable DLC folder — trusting it blindly lets a leaked/copied DLC folder edit `steamDlcAppId` down to `0` to bypass ownership entirely. `games/multigame.json` is **not** meaningfully more protected either (Steam's file-integrity check is manual/player-triggered, not a runtime guarantee). `GameScanner.Scan` supports 3 escalating tiers (trust decision isolated in the pure, unit-tested `GameScanner.IsDlcClaimTrusted`, separate from `Scan`'s directory/file-I/O):
  - **No trust data** — each game's claimed `steamDlcAppId` trusted outright. Fine for single-deploy builds with no DLC-gated games.
  - **Unsigned `gameDlcAppIds` map** (`games/multigame.json`, `gameId → expected steamDlcAppId`, publisher-authored) — *soft* cross-check: a `gameId` present must match; absent → still trusted as declared. Closes "edit one field" but not "edit field + map entry together" — not tamper-proof.
  - **Signed map** (`DlcMapSigner.EmbeddedPublicKeyBase64`, compile-time const, mirrors `AchievementSigner.EmbeddedPublicKeyBase64`) — real ECDSA-P256 tamper-evidence. **Deliberately never config-driven** (a config-hosted key lets a tampered install supply its own matching keypair + forged map). Embedded key = source edit + rebuild only, no config.json equivalent. Opt-in = that constant non-null; `GameDlcAppIdsSignature` (base64 ECDSA-P256 sig, sealed via `pub-utils --seal-dlc-map`) is meaningless without it. **Fails closed**: missing/invalid signature → every scanned game invalid, never silently downgrades to a weaker tier (a corrupted signature must look identical to "protection intentionally disabled"). Signature verifies → map is the sole *complete* source of truth: every game must appear (bundled too, value `0`) with a matching `steamDlcAppId`, or rejected — closes the "downgrade both the claim and the map entry together" loophole.
  - Rejected entry = invalid like a missing ROM/corrupt config: logged via `Logger.LogAlways`, never shown on screen. None of this substitutes for Steam's own depot-delivery boundary (a fully repacked/cracked install is a different threat, outside any client-side check). Not about confidentiality either — `steamDlcAppId` is public Steam data (visible on the store page) — only about authentication.
- **`GameContext`** (`GameContext.cs`): identifies one game's content root, keeps single-game mode byte-identical. Per-game path methods (`ConfigLoader.Load`/`Save`, `AchievementConfigLoader.Load`, `MainMenuScreen.ResolveAssetPath`) take trailing optional `GameContext? ctx = null` — omitted (every single-game call site) → same exe-relative resolution as always. `GameContext.ResolvePath(path, ctx)`: absolute paths pass through; relative paths resolve against `ctx.RootDirectory` (set) or `AppContext.BaseDirectory` (`ctx` null). Per-game `user.json` keyed by stable `GameId` (`%APPDATA%\NEShim\Games\<gameId>\user.json`), not the mutable/dual-purpose `WindowTitle` single-game uses — never collide.
- **Bootstrapping** (`NEShimApp.cs`): `InitializeEmulator()` dispatches `InitializeEmulatorSingleGame` vs `InitializeEmulatorMultiGame` on `MultiGameMode.IsActive`. Both the once-per-process single-game boot and every carousel selection funnel through one Template Method, `LoadGameContent(GameContext? ctx)` — loads config/ROM/saves/sidebar art, calls `UnloadCurrentGame()` first (no-op first time). `LoadGame(GameContext)` = presentation half: re-applies render options, restarts audio, rebuilds menus, starts emulation. Only engine-level singletons (`_input`, `_gamepadDevice`, `_frameBuffer`, `_renderer`, `_overlayRenderer`) survive a game switch; `EmulationThread` always freshly reconstructed (captures its `AppConfig` ref once at construction).

**Carousel**: `GameCarouselScreen`/`GameCarouselRenderer` follow the same state-object + stateless-renderer split as `LogoScreen`/`LogoRenderer`, via the existing `IMenuSceneProvider` pull-scene chain — not the fuller `Screen`+`ScreenHandler` machinery (carousel is a flat list, no sub-screens).

- **Filmstrip layout**: `ComputeSlotGameIndices(selectedIndex, gameCount, visibleSlotCount)` maps state → per-slot game via plain modulo wraparound; library smaller than `visibleSlotCount` repeats naturally (same neighbor reachable from either side). Exception: the centered game never repeats in a non-center slot (`NoGame` instead, skipped by `DrawStatic`/`DrawSliding`) — 1-game library: only centered slot, both neighbors empty (`MoveNext`/`MovePrevious` no-op, no slide-to-same-tile animation); 2-game library: other game on both sides of center, next slot out on each side empty.
- **Owned resources**: `GameCarouselScreen` is `IDisposable` — owns per-game thumbnail surfaces (loaded once at construction via `MainMenuScreen.ResolveAssetPath(game.ThumbnailPath, GameContext.ForGame(...))`; missing file → placeholder card, not an error) + optional `AnimatedImagePlayer` background (`AnimatedImagePlayer.cs`: GIF/WEBP/APNG or static image, wall-clock-timed; backed by `SdlSurfaceLoader.LoadAnimationFromFile`, thin wrapper over SDL3_image's `Image.LoadAnimation`/`FreeAnimation`, no new dependency).
- **Background rendering**: via `SDL3PaintContext.BlitSurfaceUncached`, not the cached `BlitSurface`/`BlitSurfaceAlpha` thumbnails use — a background frame's surface pointer can mean different pixel content over time, so pointer-caching would freeze the first-uploaded content (`RenderSurface._textureCache` is only safe for static one-shot surfaces like thumbnails/box art). Re-uploaded every frame → `AnimatedImagePlayer.LoadFromFile`'s `maxWidth`/`maxHeight` (= ctor `viewportWidth`/`viewportHeight`, from `SDL3WindowHost.ClientWidth`/`ClientHeight`) downscale every decoded frame to actual window size at load time, never upscale — bounds re-upload cost to the real render target (background must fill anything from 720p to 4K, unlike a fixed-size thumbnail).
- **Animation timing**: Left/Right selection + Up-to-flip-description card animate via `SlideProgress`/`FlipProgress`, computed from wall-clock elapsed time on every access (same convention as `LogoScreen.CurrentAlpha`) — backed by pure, unit-tested `ComputeSlideProgress`/`ComputeFlipProgress`/`ComputeFlipVisual`/`ComputeBoxArtRect`, mirroring `LogoRenderer.ComputeDisplayRect`.
- **Scanning and error entries**: `GameScanner.Scan(gamesRoot)` enumerates `games/*/config.json` (independent of `MultiGameMode.IsActive`'s manifest detection — `games/` can have zero valid subfolders while multi-game mode is still active, e.g. DLC still downloading). Never skips a folder: missing/unparseable `config.json` or unresolvable `RomPath` → `GameManifest{IsValid:false}` instead of dropped, so carousel shows a generic "Game Error" note (`LocalizationData.CarouselUnavailable`); `Confirm()` no-ops on invalid entries. Specific reason deliberately not carried on `GameManifest`/shown on screen (broken entry is almost always a Steam download issue Steam itself flags, or a publisher packaging mistake — a player needs neither detail) — but always logged to `neshim.log` via `Logger.LogAlways` (not gated behind `EnableLogging`), recoverable for support even from default config. Missing thumbnail ≠ validity failure.

**Carousel localization**: unlike v1, `GameCarouselScreen`/`GameCarouselRenderer` are fully localized — `NEShimApp.InitializeCarousel()` calls `LoadLocalization()` (depends only on `_config.Language`, already set from shell manifest) before scanning/constructing, passes result to `GameScanner.Scan` + the `GameCarouselScreen` ctor (exposed as `.Localization`, read by renderer — same shape as `MainMenuScreen`/`InGameMenu` minus `UpdateLocalization`, since carousel fully reconstructs on every entry). All 10 `lang/*.json` carry the full key set (`LangFileValidationTests.cs` enforces exact key match to `english.json`). Renderer scales title/placeholder-glyph size by tile slot scale (`ScaledTitlePtSize`, floored so far-offset tiles stay legible); omits old game-count/arrow-glyph hints (centered/highlighted tile already conveys selection). Both `MainMenuScreen`/`InGameMenu` gain a "Change Game" item (shown only when `MultiGameMode.IsActive`, each gated by its own `HasChangeGame` check) — eagerly tears down current game (`UnloadCurrentGame()`) → fresh carousel; distinct from "Return to Main Menu" (in-game only, stays in-game). `InitializeCarousel()` reloads `_config` from `MultiGameMode.ManifestPath` every run (not just first boot) so shell fields (e.g. `CarouselBackgroundPath`) don't leak the just-exited game's config.

## Publishing Checklist

Before building a release for a specific game:

- **Window title**: `WindowTitle` in `config.json` = game's name.
- **Language**: `lang/*.json` ships alongside exe. Active language read from Steam at startup; `language` in `config.json` = fallback for non-Steam launches. 10 built-in (english, french, german, spanish, latam, japanese, korean, russian, schinese, portuguese). Translated achievement names go in the Steamworks dashboard (unlock notification pulls the display name from Steam automatically).
- **Exe icon**: `<ApplicationIcon>path/to/icon.ico</ApplicationIcon>` in `NEShim/NEShim.csproj` + valid `.ico` at that path. Controls icon in Explorer/taskbar/alt-tab/Steam. No runtime icon config — only the compile-time embedded icon affects the exe file icon + Steam library entry.
- **Signing keypair**: `pub-utils --gen-keypair` once per game. Public key → `achievementPublicKey` in `config.json` (pre-built) or `AchievementSigner.EmbeddedPublicKeyBase64` + rebuild (source). Private key outside source control. No key configured = achievements disabled, no shipped default.
- **Achievements**: edit `achievements.json` → `pub-utils --key-file private_key.txt achievements.json` (stamps ECDSA-P256 sigs). Re-seal on any definition change.
- **steam_appid.txt**: output-dir file must hold the real Steam App ID (not `0`) — read by both `SteamAPI.RestartAppIfNecessary` and `SteamAPI.Init`. Dev source-tree copy = `0` (skips restart, still inits if Steam running); publish pipeline must swap in the real ID.
- **Steamworks native library**: not in repo. After `dotnet publish`, copy from the [Steamworks.NET release zip](https://github.com/rlabrecque/Steamworks.NET/releases): `steam_api64.dll` for Windows (`win-x64`). Linux (`linux-x64`): copy the zip's `libsteam_api.so`, **rename to `libsteam_api64.so`** (see "Linux native lib naming gotcha" — wrapper's `DllImport` resolves to that name, silently fails `SteamAPI_Init` otherwise). Use the wrapper-matched copy; don't pull from the Steamworks SDK partner dashboard.

### Publishing Checklist — multi-game

Additive — needs every single-game item above done once per game, plus:

- **`games/multigame.json`**: ship with the base engine publish (`local-publish.ps1` output) — its presence alone activates multi-game/carousel mode (see Multi-Game Mode above). Not auto-created by any script — author by hand (same `AppConfig` schema as `config.json`; only window/language/`NoLogo`/`carouselBackgroundPath` are meaningful here). `carouselBackgroundPath` relative to `games/`, static image or animated GIF.
- **Per-game content**: build each `games/<gameId>/` via `local-publish-game.ps1` (`-GameId`, `-SourceDir`, `-OutDir` or `-EngineOutDir`) — separate from + in addition to the engine binary publish. Set `thumbnailPath` (box art, ~1.42:1 aspect) + `gameDescription` (carousel flip-card back) in the game's `config.json` — both optional; missing thumbnail → placeholder card, not a blocker.
- **DLC vs. bundled, per game** (independent choice each game): `steamDlcAppId` default `0` = bundled directly in base install/depot (shows unconditionally, no Steamworks setup) — fine for a fixed anthology, or even every game in a build for a zero-DLC-depot release. Or: create a Steam Partner DLC depot for that `games/<gameId>/` folder, set the depot's App ID as `steamDlcAppId`, to sell/gate separately. Freely mixable.
- **DLC anti-tamper — unsigned tier** (optional, recommended minimum for any DLC-gated game): add each nonzero-`steamDlcAppId` game to `games/multigame.json`'s `gameDlcAppIds` (`gameId → App ID`, e.g. `"gameDlcAppIds": { "kaaz": 3010000 }`). No entry → per-game `steamDlcAppId` trusted as-is (bypassable by editing a leaked config.json down to 0). Bundled games (0) need no entry.
- **DLC anti-tamper — signed tier** (optional, real tamper-proofing, recommended for real commercial DLC): `pub-utils --gen-keypair` — **fresh keypair, do NOT reuse the achievement-signing one** (different protection domains; a leaked/rotated key for one must never force touching the other; a 2nd keypair is free). Compile the public key into `NEShim.Signing/DlcMapSigner.cs`'s `EmbeddedPublicKeyBase64`, rebuild from source — **deliberately never config-driven** (no `games/multigame.json`/`config.json` equivalent). Seal: `pub-utils --seal-dlc-map --key-file private_key.txt games/multigame.json` (writes `gameDlcAppIdsSignature` in place). Once the embedded key is set: `gameDlcAppIds` must be *complete* (every game listed, bundled ones = `0`) or rejected; any signature problem (missing, or map changed since sealing) → *every* game rejected, fail-closed. Re-run `--seal-dlc-map` whenever `gameDlcAppIds` changes.
- **Achievement `steamId` namespacing**: all N games share one Steam base App ID → one Steamworks achievement schema — prefix `steamId`s per game (e.g. `KAAZ_ACH_WIN` vs `GAME2_ACH_WIN`) to avoid collisions.
- **Compile-time achievement key**: `AchievementSigner.EmbeddedPublicKeyBase64` must stay `null` for multi-game builds (no single correct key across N games' `achievements.json`s). Each game's own `AchievementPublicKey` in its `config.json` resolves at runtime instead (existing `AchievementConfigLoader` precedence).
- **`steam_appid.txt` / `game_actions_<appid>.vdf`**: unchanged from single-game — both stay singular/app-wide (one Steam base App ID, one process).
